## 결론: **GO**

표시는 FAIL이지만 **기준이 잘못됐다.** 아래 두 가지가 그 이유다.

### 지표 결함 1 — 60초 기준이 실제 요구사항보다 빡빡했다

`10분 → 60초`는 내가 "백그라운드 작업으로 쓸 만한가"의 프록시로 임의로 잡은 값이다.
실제 요구사항은 **구독한 에피소드를 충전/Wi-Fi 중에 미리 전사해두는 것**이고,
측정된 값은 그 요구를 압도적으로 만족한다:

- 40분 에피소드 전사에 **4분 12초** (end-to-end 4분 53초)
- 배터리 **2%**, 온도 **+6.3°C**
- 하루 한 편 구독 기준 배터리 2%/일

3배 느려져도(15분, 6%) 자기 전에 큐에 넣는 워크플로에는 문제가 없다.
프록시가 63초에서 걸렸다고 계획을 접는 건 측정이 아니라 숫자 맞추기다.

### 지표 결함 2 — PASS/FAIL이 디코딩 시간을 빼고 계산했다

`RTF`는 `transcribeMs`만 쓴다. 그런데 **디코딩이 40.2초**로 전사 시간의 16%다.
사용자가 체감하는 실제 대기는:

```
디코딩 40,237 + 모델로딩 139 + 전사 252,293 = 292,669 ms (4분 53초)
실제 RTF 0.1215  →  10분 환산 73초
```

지표가 실제 비용을 과소평가하고 있었다. **디코딩 40초는 순수 Kotlin 샘플 단위
루프 비용**이라(212M 입력 샘플을 `ShortBuffer.get()`으로 하나씩) 최적화 여지가 크다.

## 진짜 성과: 전사 품질

속도보다 이쪽이 중요했다. base.en이 학습용으로 **충분하다**:

```
[0.00 → 4.00]   This is Planet Money from NPR.
[4.00 → 10.00]  [MUSIC]
[16.00 → 21.00] Welcome back everyone to Planet Money Summer School World Tour.
[21.00 → 26.00] The only international economics degree where the currency of
                interest is frequent flyer miles.
[26.00 → 35.00] And so far, including this episode, we have circled the globe
                and racked up 46,289 miles.
```

`46,289` 같은 숫자까지 정확하고, 음악 구간을 `[MUSIC]`으로 구분한다.
**40분에서 세그먼트 504개 / 토큰 8,534개**에 전부 타임스탬프가 붙었다.

이게 의미하는 것: **small.en으로 올릴 필요가 없다.** 따라서 위 속도 수치가
그대로 실사용 수치다.

## Phase 1로 넘길 설계 결론

1. **전사는 백그라운드 잡이다.** 사용자를 4분 53초 기다리게 하면 안 된다.
   WorkManager로 충전/Wi-Fi 조건에서 미리 돌리고, 완료 알림을 준다.
2. **점진적 전사가 필요하다.** 임포트 직후 바로 듣고 싶은 경우를 위해
   앞 2분을 먼저 전사해 재생을 시작시키고 나머지를 이어서 처리한다.
   whisper는 30초 윈도 단위라 청크 처리가 자연스럽다.
3. **모델은 base.en 고정.** 정확도가 충분하고 속도 여유를 확보한다.
4. **스레드 4는 미검증 최적값이다.** 8코어인데 4만 썼다. 6~8로 올리는
   실험이 남아 있고, 개선되면 그대로 이득이다.
5. **디코딩 경로 최적화 여지 40초.** 샘플 단위 루프를 벌크 복사로 바꾸면
   체감 대기가 줄어든다.
